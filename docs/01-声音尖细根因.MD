# 声音尖细、语速过快的根因

## 现象

`watchdog.service` 播放恢复语音时，声音明显尖细，语速也明显变快。对原音频做“放慢”处理后，问题仍然存在。

## 已验证的根因

根因是**播放端实际使用的采样率与 WAV 文件中的采样率不一致**。

- `sounds/1.wav` 的格式是：PCM、16-bit、单声道、**24000 Hz**。
- 板端 ES8388 播放链路按约 **44100 Hz** 消耗采样点。
- 24 kHz 的采样数据直接按 44.1 kHz 播放时，采样点被更快地消耗，结果就是：
  - 播放时长缩短；
  - 语速变快；
  - 音调整体升高，听感变尖、变细。

试听验证：

1. 直接播放 24 kHz 的 `1.wav`，板端听到“非常尖、非常细、语速超级快”。
2. 将同一文件**真正重采样**为 44100 Hz 后再播放，问题消失，语音速度和音调恢复正常。

## 为什么之前的处理没有解决

以下操作不能解决这个问题：

- 只修改 WAV header 中的采样率；
- 只把音频时间轴拉长，但没有重新生成与播放设备匹配的采样点；
- 只在播放器参数中声明 24000 Hz，却不确认 ALSA/硬件最终采用的实际 rate。

这些操作可能只是改变元数据或播放时序，并没有保证硬件以正确的采样率输出。

## 正确修复方式

将语音文件离线重采样到板端稳定使用的 44100 Hz，保持 PCM 16-bit、单声道：

```bash
ffmpeg -i sounds/1.wav \
  -ar 44100 -ac 1 -sample_fmt s16 \
  sounds/sixcam_recover.wav
```

重采样后应检查：

```bash
ffprobe sounds/sixcam_recover.wav
```

应看到：

```text
Audio: pcm_s16le, 44100 Hz, mono
```

## 板端试听验证命令

以下命令在开发机执行。它们不会覆盖 `/etc/watchdog/sounds/` 中的正式文件，只把测试文件放到板端 `/tmp`。

先确认设备并停止 watchdog，避免服务占用声卡：

```bash
adb devices
adb shell 'systemctl stop watchdog'
```

### 1. 播放原始 24 kHz 文件

```bash
adb push 02-github/watchdog/sounds/1.wav /tmp/watchdog-1-24k.wav
adb shell 'aplay -D plughw:CARD=rockchipes8388,DEV=0 /tmp/watchdog-1-24k.wav'
```

此版本预期会出现语速过快、音调尖细，用于复现问题。

### 2. 生成并播放正确的 44.1 kHz 文件

在开发机执行真正的重采样：

```bash
ffmpeg -y -i 02-github/watchdog/sounds/1.wav \
  -ar 44100 -ac 1 -sample_fmt s16 \
  /tmp/watchdog-1-44k.wav
```

检查格式：

```bash
ffprobe /tmp/watchdog-1-44k.wav
```

然后推送并播放：

```bash
adb push /tmp/watchdog-1-44k.wav /tmp/watchdog-1-44k.wav
adb shell 'aplay -D plughw:CARD=rockchipes8388,DEV=0 /tmp/watchdog-1-44k.wav'
```

如果这个版本仍然明显变快，说明问题不止是 WAV header，继续执行下面的直通/插件对照测试，不要继续盲目改采样率。

### 2.1 `plughw` 与 `hw` 对照测试

先停止 watchdog，并确认测试文件存在：

```bash
adb shell 'systemctl stop watchdog'
adb shell 'ls -l /tmp/watchdog-1-44k.wav'
```

使用 ALSA plug 层播放：

```bash
adb shell 'aplay -D plughw:CARD=rockchipes8388,DEV=0 /tmp/watchdog-1-44k.wav'
```

再使用硬件直通播放：

```bash
adb shell 'aplay -D hw:CARD=rockchipes8388,DEV=0 /tmp/watchdog-1-44k.wav'
```

判断方式：

- `plughw` 正常、`hw` 尖快：问题在硬件直通时的采样率/时钟配置；
- 两者都尖快：问题可能在 ES8323 的物理 MCLK/BCLK、设备树或音频源文件本身；
- 两者速度不同：记录两次播放时的 `hw_params`，不要只看 WAV header。

播放期间另开终端查看实际参数：

```bash
adb shell 'cat /proc/asound/card0/pcm0p/sub0/hw_params'
```

测试期间保持 watchdog 关闭：

```bash
adb shell 'systemctl stop watchdog; systemctl disable watchdog'
adb shell 'systemctl is-active watchdog || true'
```

只有确认修复完成后，才手动恢复：

```bash
adb shell 'systemctl enable watchdog'
adb shell 'systemctl start watchdog'
```

### 4. 确认板端实际 PCM 参数

在播放过程中另开一个终端执行：

```bash
adb shell 'cat /proc/asound/card0/pcm0p/sub0/hw_params'
```

重点查看：

```text
format: S16_LE
channels: 1
rate: 44100
```

## 正式替换与回滚（确认试听正常后再执行）

用 44.1 kHz 文件替换六目恢复音，并保留原文件：

```bash
adb shell 'cp -f /etc/watchdog/sounds/sixcam_recover.wav /etc/watchdog/sounds/sixcam_recover.wav.bak'
adb push /tmp/watchdog-1-44k.wav /tmp/sixcam_recover.wav.new
adb shell 'install -m 0644 /tmp/sixcam_recover.wav.new /etc/watchdog/sounds/sixcam_recover.wav'
adb shell 'systemctl stop watchdog; systemctl disable watchdog'
```

回滚：

```bash
adb shell 'cp -f /etc/watchdog/sounds/sixcam_recover.wav.bak /etc/watchdog/sounds/sixcam_recover.wav'
adb shell 'systemctl stop watchdog; systemctl disable watchdog'
```

## 代码侧防回归

`src/audio.cpp` 中使用 `snd_pcm_hw_params_set_rate_near()` 后，应读取并记录 ALSA 最终采用的 rate；如果实际 rate 与 WAV rate 不一致，应明确报错或执行可靠的重采样，不能静默继续播放：

```cpp
unsigned int actual_rate = 0;
snd_pcm_hw_params_get_rate(hw, &actual_rate, nullptr);
log_info("audio: requested_rate=%u actual_rate=%u",
         wav.sample_rate, actual_rate);
```

## 当前结论与待确认项

24 kHz 文件被错误地按 44.1 kHz 消耗，确实可以完整解释“语速快、音调尖细”，但如果真正重采样为 44100 Hz 后仍然出现同样现象，则不能再把采样率失配视为唯一根因。

此时必须通过上面的 `plughw` / `hw` 对照实验继续确认：

- ALSA plug 层是否真的执行了采样率转换；
- ES8323 的实际 MCLK/BCLK 是否与内核报告的 44100 Hz 一致；
- 音频文件的采样点是否在生成阶段已经被加速或变调。

在这些对照结果出来前，不应直接覆盖正式语音文件，也不应只通过修改 WAV header 继续试错。

## 深度定位结果：单声道被硬件按双声道 slot 消耗

进一步在板端测量了实际播放耗时：

- 44100 Hz、单声道、约 2.98 秒的 WAV，`hw:CARD=rockchipes8388,DEV=0` 实际约 1.55 秒播放完；
- 将同一音频复制为 44100 Hz、双声道后，实际约 3.05 秒播放完。

这证明问题不是原始语音内容，也不是简单的 24 kHz/44.1 kHz 文件 header，而是 **ES8323/I2S 播放链路要求双声道 frame slot，而 watchdog/测试文件以单声道 frame 写入**。单声道数据被按双 slot 的时钟消耗，导致约 1.9 倍速、音调尖细。

复现/验证命令：

```bash
# 单声道：会明显变快
adb shell 'date +%s%3N; aplay -D hw:CARD=rockchipes8388,DEV=0 /tmp/watchdog-1-44k.wav >/tmp/mono.log 2>&1; date +%s%3N'

# 将单声道复制成双声道：速度应恢复正常
ffmpeg -y -i /tmp/watchdog-1-44k.wav -ac 2 -ar 44100 -sample_fmt s16 /tmp/watchdog-1-44k-stereo.wav
adb push /tmp/watchdog-1-44k-stereo.wav /tmp/watchdog-1-44k-stereo.wav
adb shell 'date +%s%3N; aplay -D hw:CARD=rockchipes8388,DEV=0 /tmp/watchdog-1-44k-stereo.wav >/tmp/stereo.log 2>&1; date +%s%3N'
```

正式修复应在 `src/audio.cpp` 中对单声道 WAV 做左右声道复制，并以 2 channels、interleaved S16_LE 写入 ALSA；不能只把 WAV header 的 channel 数改成 2，否则会造成数据长度/帧布局错误。
